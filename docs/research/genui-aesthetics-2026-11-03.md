# GenUI 组件美学调研

调研日期：2026-11-03。范围为中英文 ChatGPT Intelligent UI 拆解、OpenAI 官方界面规范、公开组件库和声明式生成 UI 框架。结论结合本仓库当前源码及既有预算、选购截图；截图用于观察既有视觉，不代表本轮重新运行后的实时页面。

## 结论与项目适配

建议把美学改进分成三个可独立评审的部分：组件自身的视觉质量、组件之间的组合规则、内容与交互的主次。当前项目已经具备固定组件目录和声明式校验，适合先建设统一设计规范，再完善模型选择组件与布局的指导。

项目现状：React 19、TypeScript、Vite；组件样式通过本地 CSS 注入 Shadow DOM；模型生成 v3 JSON，渲染器处理白名单组件；state/derived 与 AST 求值支持本地联动。没有 Tailwind 或外部 UI 组件库依赖。

在这个架构中，提示词可以影响布局和内容顺序，但不能改变控件的绘制方式、字体、间距或阴影。单纯要求模型“设计得更高级”不能替代本地组件样式的改进。

## 值得阅读的资料

### 1. 最贴近问题的技术拆解

[How ChatGPT Intelligent UI works — Thesys / OpenUI](https://www.openui.com/blog/how-chatgpt-intelligent-ui-works)，2026-10-08。

重点阅读 Design system and catalog、Rendering 和 On the client。作者根据自己的网页流量、前端代码及实验观察，描述了组件目录、设计令牌与宿主渲染的配合。这支持一个值得借鉴的思路：让模型负责组合受约束的组件，视觉一致性由宿主负责。

可信度边界：这是作者的一手逆向观察，不是 OpenAI 官方架构规范；观察针对当时的网页端，不能外推为所有客户端的永久实现。本文不把文中组件数、内部语言或动画时长作为项目约束。

### 2. 官方的嵌入式界面视觉规范

[UI guidelines — OpenAI Developers](https://developers.openai.com/plugins/concepts/ui-guidelines)。

重点是系统字体、克制的颜色、稳定的间距、清晰的内容层级、有限的主操作，以及避免界面与正文重复。它直接讨论对话流中的组件如何保持熟悉、易读和可操作。

适用边界：这是 ChatGPT 插件/应用界面的指南，不是 Intelligent UI 内部实现的公开规范。对本项目应借鉴视觉与交互原则，并与 DeepSeek 的明暗主题协调；不机械套用 ChatGPT 的专属品牌、展示模式和宿主接口要求。

### 3. 可检查实现的官方组件库

[Apps SDK UI — OpenAI](https://github.com/openai/apps-sdk-ui)。

公开库提供 React 组件及与 Tailwind 配合的设计令牌，可以用于研究按钮、表单、提示、排版等基础细节。官方指南也将其列为可选工具。

项目建议：先参考它的规范与组件细节。是否引入依赖需另做打包、样式隔离及现有行为验证，不把换库作为美学改进的前提，也不把此库当作 Intelligent UI 完整内部实现。

### 4. 关于 GPT 生成界面质量的官方分析

[Designing delightful frontends with GPT-5.4 — OpenAI Developers](https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4)。

文章讨论了明确设计约束、视觉参照、内容策略和验证的重要性。其中 Apps 部分提倡克制的界面层次、清楚的排版和较少的装饰。对本项目，应使用应用界面相关建议；其中面向营销网站的大图、品牌首屏等指导不应直接用于聊天中的工具卡片。

### 5. 与当前架构相近的框架参考

[json-render 文档](https://json-render.dev/docs)、[Google A2UI 介绍](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/)。

两者都提供组件目录/声明描述与客户端渲染分离的参考。与本项目最相关的是：保留由开发者控制的组件实现，让生成过程在目录和类型约束中组合布局。这是架构上的参考，不说明它们与本项目的协议、状态模型或交互能力相同。

## 从现有实现观察到的问题

以下为源码与截图审阅后的设计判断，不是用户研究或性能测量结果。

| 位置 | 当前观察 | 建议 |
| --- | --- | --- |
| 卡片标题与正文 | 卡片标题与根正文均为 14px；区域标题为 13px | 建立明确且克制的标题、正文、辅助文字层级，结合字重和留白区别主次 |
| 关键数值 | value 多为等权重标签和值的一行展示 | 改善数字、单位与标签的排版；重要结果需要有明确的强调方式 |
| 卡片与 section | 外壳和每个 section 都有描边，section 可嵌套 | 用留白组织常规分组，只在有独立交互意义时保留内层容器 |
| 间距与配色 | 大量数值和灰色透明度分别写在选择器里 | 用语义化 CSS 变量集中管理表面、正文、边界、状态色、间距与圆角 |
| 页脚 | 重置、继续讨论、原始 JSON 同时呈现；另有较长技术说明 | 区分主要操作与辅助入口，技术说明逐步披露，保持原始内容可访问 |
| 图表 | 有固定多色调色板，SVG 轴标签较小 | 根据系列语义使用颜色，核对暗色对比与缩放后的可读性，保留查看数据入口 |
| 表格 | 宽表需要横向滚动，工具栏与边框密度较高 | 优先改善列宽、数值对齐、表头和筛选状态，避免仅靠增加圆角美化 |
| 响应布局 | columns 按视口宽度切换单列 | 评估按卡片可用宽度调整，覆盖宽屏中聊天栏实际很窄的情况 |

主要源码：`src/render/card.css`、`src/render/Card.tsx`、`src/render/interactive.tsx`、`src/render/composite.tsx`、`src/render/charts.tsx`、`src/render/table.tsx`、`src/render/theme.ts`、`src/render/mount.tsx`。

## 建议实施顺序

### 第一轮：统一已有组件的视觉

- 建立亮/暗两套语义颜色与间距变量；延续已有站点主题检测。
- 梳理标题、正文、数值、单位、辅助信息的层级，不增加大量字体尺寸。
- 统一按钮、输入框、select、slider 的外观和 hover/focus/disabled/error 状态。
- 减少多层描边和同权重灰底；强化真正重要的结果和操作。
- 同步处理图表、表格与提示框，避免仅更新外层 Card。

本轮优先使用已有协议表达能力；视觉改进主要在本地渲染器完成。

### 第二轮：改善组合与语义表达

- 预算：参数 → 关键结果 → 图表与明细。
- 选购：条件 → 对比信息 → 决策依据。
- 数学学习：系数 → 曲线 → 解释与原始采样数据。

这些是组合规则，不是把所有问题路由到固定模板。若需要新增“主要指标”“强调程度”“布局密度”等字段，需明确标为新能力，做 Schema、提示词、旧版本兼容及渲染验证；当前协议尚未提供这些字段。

### 第三轮：视觉与交互验收

以现有三类示例建立相同数据、相同视口的前后对照，检查亮/暗主题、窄聊天栏、长中文、单位、空结果、输入错误和重置。检查重点包括：能否立即找到核心结果、操作是否有主次、文字对比是否足够、缩放与换行是否稳定、用户调整时是否发生布局跳动。

保留已有本地求值、状态隔离、原始 JSON 查看及用户自行发送的行为。对视觉状态的验证应结合截图与实际交互；现有类型检查和功能单测不能证明美学质量。
